最值得避免的坑是：**直接把 MySQL/PostgreSQL/数仓的几十上百张表通过 MCP 暴露给 Agent**

这样短期能跑，后面一定会遇到选错表、指标口径冲突、JOIN 错误、权限失控、SQL 成本不可控。

> MCP 本身正好提供了一个很合适的分层：[Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/index) 用于向模型提供上下文和数据描述，`Tools` 用于让模型真正执行查询或操作；官方定义中 Resources 偏应用控制，Tools 偏模型调用。 所以你的“数据地图”应该主要成为 **Resource/Metadata 层**，而不是把所有东西都变成 Tool。

我把它定义成 **AAMS 的“企业数据地图层”**：它不是简单的数据库表目录，而是专门告诉 Agent——**公司有哪些数据、业务含义是什么、去哪里查、怎么查、能不能查、结果是否可信。**

## 企业数据地图层
### 一、终要做成什么
```tex
                         AAMS Agent
                             │
                 ┌───────────▼───────────┐
                 │    Enterprise MCP     │
                 │                       │
                 │  数据发现 / 数据理解   │
                 │  指标查询 / 明细查询   │
                 │  权限控制 / 查询审计   │
                 └───────────┬───────────┘
                             │
              ┌──────────────▼──────────────┐
              │          数据地图            │
              │                              │
              │  Domain      业务域          │
              │  Entity      业务实体        │
              │  Metric      指标            │
              │  Dataset     数据集/表       │
              │  Field       字段            │
              │  Relation    数据关系        │
              │  Lineage     数据血缘        │
              │  Permission  权限            │
              └──────────────┬──────────────┘
                             │
        ┌────────────┬───────┼────────┬───────────┐
        ▼            ▼       ▼        ▼           ▼
      ERP          OMS      WMS     Amazon       广告
      财务         订单     库存     Wayfair      物流
                                   Shopify...
```

数据地图实际上解决的是：

> **业务问题 → 业务指标 → 业务实体 → 数据集 → 字段 → 查询方式**

而不是：

> Agent → 猜 SQL → 查数据库

这一点非常重要。

### 二、数据地图设计成 6 层

**第一层：Domain——业务域**

不要先从数据库表开始整理。

先把公司的业务划分出来。

结合家具跨境电商业务：

| Domain     | 中文   | 主要内容               |
| ---------- | ------ | ---------------------- |
| Sales      | 销售   | 订单、销售额、渠道     |
| Product    | 商品   | SPU、SKU、类目、尺寸   |
| Inventory  | 库存   | 海外仓库存、在途库存   |
| Logistics  | 物流   | 发货、妥投、时效       |
| AfterSales | 售后   | 退款、退货、赔偿       |
| Marketing  | 营销   | 广告、流量、转化       |
| Finance    | 财务   | 收入、成本、毛利       |
| Customer   | 客户   | 买家、地域、复购       |
| Supplier   | 供应链 | 采购、供应商、采购成本 |

[OpenMetadata](https://docs.open-metadata.org/v1.12.x/how-to-guides/data-governance/domains-%26-data-products?utm_source=chatgpt.com)、DataHub 这样的数据目录产品本质上也都在往 Domain、Glossary、Lineage、Data Product 这一方向组织企业数据，而不是单纯展示数据库 schema。

### 三、第二层非常重要：Business Entity

Domain 下面不要直接挂表。

要先建立**业务实体**。

例如：

```
Sales
 ├── Order
 ├── OrderItem
 ├── Channel
 └── Store

Product
 ├── SPU
 ├── SKU
 ├── Category
 └── ProductCost

Inventory
 ├── Warehouse
 ├── Inventory
 └── InboundShipment

Logistics
 ├── Shipment
 ├── Package
 ├── Carrier
 └── TrackingEvent
```

比如：

```yaml
entity:
  id: sales.order
  name: Order
  display_name: 销售订单

  description: >
    客户在各销售渠道产生的一次购买行为。

  primary_key:
    business_key: order_no

  source:
    dataset: dwd_order
    field: order_no

  relationships:
    - entity: sales.order_item
      type: one_to_many

    - entity: customer.customer
      type: many_to_one
```

这样 Agent 才知道：

> Order 是一个业务概念。

而不是：

> `ods_amz_order_v2` 好像是一张订单表。



四、第三层：Metric——指标地图

这一层对你的 AAMS **比数据库地图还重要**。

因为业务 Agent 大部分问题其实不是：

> 查询订单表。

而是：

> 最近7天美国站销售额为什么下降？

这里涉及：

```
销售额
订单数
销量
ASP
退款金额
广告销售额
库存缺货率
转化率
```

所以建议单独建立：

```
Metric Registry
```

例如：

```yaml
metric:
  id: sales.gmv

  name: GMV
  display_name: 商品交易总额

  domain: sales

  description: >
    成功创建订单的商品成交金额，
    不扣除退款。

  formula:
    sum(order_item.quantity * order_item.unit_price)

  source:
    dataset: dwd_order_item

  dimensions:
    - order_date
    - platform
    - store
    - country
    - sku
    - category

  filters:
    exclude_status:
      - cancelled

  owner:
    department: ecommerce

  certification:
    status: certified

  sensitivity:
    level: internal
```

再比如：

```yaml
metric:
  id: finance.net_sales

  name: Net Sales

  formula:
    GMV
    - refund_amount
    - discount_amount
```

### 五、这一层必须解决“同名指标不同口径”

企业 Agent 最容易死在这里。

比如用户问：

这个月销售额多少？

不同部门可能理解成：

```
销售额
```

可能是：

```
GMV
Revenue
Net Sales
Paid GMV
Shipped GMV
Delivered GMV
```

所以数据地图里必须存在：

```
Business Glossary
```

比如：

```
销售额
 ├── GMV
 ├── Paid GMV
 ├── Shipped GMV
 ├── Net Sales
 └── Revenue
```

每一个都有清晰定义。

这类 Business Glossary 的目标本来就是给组织建立统一受控词汇和[业务语义](https://docs.open-metadata.org/v1.12.x/how-to-guides/data-governance/glossary/glossary-term?utm_source=chatgpt.com)。

未来 Agent 收到：

> 分析最近30天销售额

它应该先判断：

```
销售额 → sales.gmv
```

而不是自己猜：

```
SUM(price)
```



### 六、第四层才是 Dataset / Table

到了这一层才开始描述数据库。

例如：

```yaml
dataset:
  id: warehouse.dwd_order

  name: dwd_order

  type: table

  domain: sales

  entity:
    - sales.order

  database: dw
  schema: ecommerce

  description: 订单事实表

  grain:
    description: 一行代表一个订单
    key:
      - order_no

  update_frequency:
    type: hourly

  freshness:
    max_delay_minutes: 60

  owner:
    team: data

  quality:
    status: certified

  sensitivity:
    level: internal
```

特别提醒你：

**一定要定义 Grain。**

也就是：

> 一行数据到底代表什么？

比如：

```
dwd_order
1 row = 1 order

dwd_order_item
1 row = 1 order + 1 sku

inventory_snapshot
1 row = warehouse + sku + date

advertising_daily
1 row = campaign + sku + date
```

Agent 自动写 JOIN 的时候，这个信息价值极高。



### 七、第五层：Field Map

字段不要只保存：

```
field_name
data_type
comment
```

至少保存：

```
字段名
业务名称
业务含义
类型
主键/外键
关联实体
示例值
枚举
敏感等级
可否查询
```

比如：

```yaml
field:
  dataset: dwd_order

  name: order_status

  display_name: 订单状态

  data_type: varchar

  description: 当前订单生命周期状态

  enum:
    pending: 待付款
    paid: 已付款
    shipped: 已发货
    delivered: 已妥投
    cancelled: 已取消
    refunded: 已退款

  filterable: true

  sensitivity: public_internal
```

这样 Agent 问：

> 查询已经发货但是没有妥投的订单

它就可以理解：

```
order_status = shipped
```



### 八、第六层：Relation + Lineage

这一层决定 Agent 能不能安全 JOIN。

例如建立：

```
Order
  │
  ├──1:N── OrderItem
  │           │
  │           N:1
  │           │
  │          SKU
  │
  N:1
  │
Customer
```

技术上存成：

```
relationship:
  from:
    dataset: dwd_order
    field: order_no

  to:
    dataset: dwd_order_item
    field: order_no

  type: one_to_many

  join:
    type: inner
```

再建立 lineage：

```
Amazon API
    ↓
ods_amazon_order
    ↓
dwd_order
    ↓
dws_sales_daily
    ↓
GMV
    ↓
Sales Agent
```

成熟的数据目录产品已经普遍支持 [table/column lineage](https://docs.open-metadata.org/v1.12.x/how-to-guides/data-lineage/explore?utm_source=chatgpt.com)，用来追踪表、字段、pipeline 和下游消费之间的关系。



### 九、真正到了 MCP 层，千万不要设计成 100 个 SQL Tool

这里我非常建议你采用：

```
Resource = 数据地图
Tool     = 数据访问能力
```

MCP 官方就把 Resources 定义成可以向客户端暴露数据库 schema、文件或应用数据等上下文，并且每个 Resource 使用 URI 标识；Resources 还支持列表变更通知等机制。

例如你可以设计：

```
resource://data-map/domains
resource://data-map/domain/sales
resource://data-map/entity/order
resource://data-map/entity/sku
resource://data-map/metric/gmv
resource://data-map/dataset/dwd_order
resource://data-map/dataset/dwd_order/fields
resource://data-map/lineage/dwd_order
```

Agent 可以逐步发现数据。



### 十、MCP Tool 我建议第一版只做 6 个

不要搞几十个。

### ① search_data_map

```
{
  "query": "订单销售额"
}
```

返回：

```
Entities:
- sales.order
- sales.order_item


Metrics:
- sales.gmv
- sales.net_sales


Datasets:
- dwd_order
- dwd_order_item
```

------

### ② describe_entity

```
{
  "entity": "sales.order"
}
```

告诉 Agent：

```
订单是什么
主键是什么
涉及哪些表
和哪些实体有关
有哪些指标
```

------

### ③ describe_metric

```
{
  "metric": "sales.gmv"
}
```

返回：

```
定义
公式
维度
过滤条件
数据来源
更新时间
负责人
```

------

### ④ describe_dataset

```
{
  "dataset": "dwd_order"
}
```

返回：

```
grain
columns
relations
quality
freshness
```

------

### ⑤ query_metric

这是以后 Agent **最应该使用的工具**。

例如：

```
{
  "metric": "sales.gmv",
  "dimensions": [
    "date",
    "platform"
  ],
  "filters": {
    "country": "US"
  },
  "date_range": {
    "start": "2026-08-01",
    "end": "2026-08-17"
  }
}
```

由你的 MCP Server 转成 SQL。

Agent **不需要知道 SQL**。

------

### ⑥ query_dataset

只有高级场景才用：

```
{
  "dataset": "dwd_order",
  "fields": [
    "order_no",
    "sku",
    "order_date"
  ],
  "filters": {}
}
```

这样至少仍然受你的字段白名单、权限和查询限制控制。

MCP Tool 本来就是模型可以发现和调用的执行能力，因此对企业环境来说，查询 Tool 应该实施权限、验证和限制，而不是简单提供任意 SQL 执行入口。MCP [官方规范](https://modelcontextprotocol.io/specification/2026-07-28)也明确强调资源访问控制以及 Tool 调用的安全控制。
