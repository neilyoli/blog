# AI Coding 之前，先让 AI 看懂项目已经有什么

最近在推进 AgentKit 时，我做了一件看起来不太像开发的事情：暂停新增功能，先把仓库里已经存在的能力重新盘点了一遍。

原因很简单。项目逐渐有了后端基础设施、企业管理功能和前端工作台。如果继续只围绕需求让 AI 写代码，很容易出现一种情况：新功能本身能跑，但实现方式绕开了项目已有的 Service、工具类和配置，最后又多出一套缓存、文件处理、日志或身份管理逻辑。

这不是 AI 不会写代码，而是它没有先弄清楚项目已经有什么。

**AI Coding 的第一步不应该总是生成代码，而应该先理解现有工程，再决定是复用、扩展还是新增。**

这次盘点最终形成了一份可复用能力资产清单，并把开发前检索的要求写进了 AgentKit 的 `AGENTS.md`。本文记录这次工作的思路、过程和一些值得注意的工程边界。

## 一、为什么需要做能力盘点

在一个持续演进的项目里，能力通常不是集中在一个地方的。

一个文件上传功能，可能涉及业务 Service、存储接口、本地实现、云存储实现和配置装配；一个用户查询，可能同时受到登录拦截器、请求上下文、数据范围插件和数据库查询的影响。

只看类名或者目录结构，很容易得出错误结论：

- 看到有 Redis，就认为已经有完整的分布式锁能力。
- 看到有心跳，就认为可以直接拿来做后台任务的存活检测。
- 看到有操作日志，就认为所有后台执行都能被审计。
- 看到有文件上传，就认为任何业务都可以直接拿 File Key 下载。
- 看到前端已经有 API 类型，就认为后端接口也已经实现。

这些判断都不可靠。**代码存在，不等于能力完整；方法可调用，不等于当前场景可以安全复用。**

如果不先做盘点，AI 很可能根据局部代码推断能力，再按自己的理解创建新的抽象。短期看起来开发很快，长期却会让同一件事出现多个入口、多个实现和不同的行为约定。

## 二、这次到底盘点了什么

本次以 AgentKit 的 `main@dcc2d85` 为代码基线，按仓库目录清点，再对关键配置、Service、AOP、拦截器、序列化器和前端 API Adapter 做源码检查。

盘点范围包括：

| 范围 | 源码现状 |
|---|---|
| 正式后端 | `agentkit-base`、`agentkit-admin` 两个 Maven 模块 |
| base | 359 个 Java 源文件，包含 common、config 和 24 个 support 功能包 |
| admin | 144 个 Java 源文件，包含登录、员工、部门、角色、菜单和数据范围等能力 |
| 前端 | 59 个 TypeScript / JavaScript 源文件 |
| POC | 独立的 Agent 运行和兼容性验证代码 |
| 历史数据库脚本 | 44 张建表定义，包含平台支撑、企业管理和历史业务表 |

这里需要说明：这些数字来自 Git 文件树统计，不代表每个文件都经过逐行审查。本次重点是识别能力入口、调用关系和容易误用的边界，而不是对所有功能做完整运行验收。

### 1. 后端公共能力

先看 `agentkit-base`。

公共层已经有不少可以直接查询和复用的入口：

- `AgentkitBeanUtil`：Bean 属性复制和校验。
- `AgentkitStringUtil`：字符串处理扩展。
- `AgentkitPageUtil`：分页参数和分页结果转换。
- `AgentkitEnumUtil`：枚举转换。
- `AgentkitIpUtil`：IP 相关处理。
- `AgentkitRequestUtil`：请求用户和 Servlet 请求上下文。
- `ResponseDTO`、`PageResult`：现有管理端响应和分页模型。

JSON 处理也不是一张白纸。Long、BigDecimal、Enum、字典、文件 Key 和脱敏序列化器都已经存在。新增 DTO 或者调整字段格式前，应该先检查 `JsonConfig` 和对应序列化器，而不是在业务代码里重新写一套转换逻辑。

### 2. 24 个 support 功能包

支撑能力是这次盘点的重点。它们分布在 `agentkit-base/module/support` 下：

| 类别 | 已有能力 |
|---|---|
| 基础数据 | 字典、系统配置、数据变更记录、表格自定义列 |
| 文件与内容 | 文件存储、帮助文档、邮件模板、站内消息 |
| 运行支撑 | Redis、Redisson、动态定时任务、进程心跳、热加载 |
| 安全辅助 | 验证码、登录失败保护、密码策略、文件类型检测、数据脱敏 |
| 系统管理 | 登录日志、操作日志、更新日志、重复提交保护 |
| 其他 | 业务序列号、反馈、API 加解密、代码生成器 |

盘点不是把这些名字抄进一张表就结束了。每项能力还需要继续确认：入口在哪里、由谁调用、依赖什么配置、是否有数据库表、运行时依赖什么上下文，以及它到底适合解决什么问题。

例如，文件服务并不只是一个上传方法。当前已有 `FileService` 和 `IFileStorageService`，后者有本地存储与 S3 云存储实现，文件业务层还负责保存文件元数据。后续业务应优先走这条入口，而不是在自己的 Service 里再创建 S3 Client、拼接本地路径和生成 URL。

### 3. admin 与前端也要纳入盘点

`agentkit-admin` 已有企业管理能力，包括登录、员工、部门、岗位、角色、菜单和数据范围。它们不应该因为新工作台出现，就被重新实现一遍。

前端也有可复用资产：登录认证上下文、路由守卫、应用壳、管理端 API、成员和角色页面、Chat / Session / Run 页面，以及 SSE 事件类型和 sequence 去重工具。

但前端有一个必须说清楚的现状：

- `admin.ts` 使用现有 Sa-Token Bearer Header，已经对接管理端接口。
- `http.ts` 实现了 `/api/v1` 的 Cookie、CSRF 和幂等请求协议，对应的 Agent 后端还没有完成正式交付。
- `mock.ts` 是开发模式使用的模拟数据和行为，不是生产后端。

把这三者混为一谈，会让开发者误以为某项功能已经端到端交付。

## 三、真正有价值的是识别复用边界

盘点过程中，有几处实现尤其值得记录。它们说明了为什么“仓库里有这个能力”并不意味着“新功能可以直接拿来用”。

### 1. Redis 操作不等于可靠的分布式锁

仓库里同时存在 `RedisService` 和 `RedissonService`。

`RedisService.getLock/unLock` 是基础 SETNX 和删除 Key 的封装，释放时没有校验锁持有者。它适合什么场景，需要结合具体使用方式判断，不能直接把它当作复杂并发任务的完整锁方案。

`RedissonService` 已经封装了 Redisson 锁操作，SmartJob 也在使用 Redisson 执行锁。新功能涉及并发控制时，应该先检查这套封装和锁的生命周期，而不是再造一个锁工具。

同时，现有 Redisson 封装对中断处理和固定租约也有需要进一步审查的地方。因此，结论不是“以后全部调用 RedissonService 就行”，而是：先识别已有实现，再根据任务的等待时间、执行时长、续期和释放语义判断是否适用。

### 2. ThreadLocal 请求身份不能直接用于后台 Agent

这是我认为本次盘点里最重要的边界之一。

当前 `AdminInterceptor` 会在 HTTP 请求中建立 `RequestUser`，并通过 `AgentkitRequestUtil` 保存到 ThreadLocal，请求结束后清理。

数据范围相关的 `DataScopeSqlConfigService` 也会读取当前请求用户。问题在于：后台 Agent 执行任务时，并没有天然的 HTTP 请求上下文。

更需要注意的是，当前数据范围实现拿不到请求用户时，会返回空的 SQL 条件。对于需要数据隔离的查询，这不能被当成安全保障。

所以，后台 Agent 不能简单调用现有请求工具，然后认为权限隔离已经生效。它需要显式传递发起人和执行身份，并在查询数据、调用工具时重新校验资源归属。身份不明确时，应拒绝执行，而不是默认放行。

### 3. 操作日志不等于 Agent 执行审计

现有 `OperateLogAspect` 通过 AOP 记录带有操作日志注解的 Controller 请求，并使用线程池异步保存日志。

它适合记录 HTTP 操作，但它依赖 `RequestContextHolder` 和请求用户上下文，不是完整的后台任务审计方案。

源码中还存在一个需要单独评估的风险：请求参数会被序列化进日志，只排除少数 Servlet 和文件类型，并没有形成通用的敏感字段脱敏机制。

密码、Token、密钥等信息不能因为“只是操作日志”就被忽略。Agent 工具执行、后台任务状态变化和用户操作也应有清楚的审计模型，不能直接把现有 AOP 当成全部答案。

### 4. 进程心跳不等于 Run 心跳

当前 `HeartBeatManager`、`HeartBeatRunnable` 记录的是 JVM 进程和服务器信息，例如服务器 IP、进程号、进程启动时间和心跳时间。

这能帮助了解服务实例是否存活，但不能证明某个 Agent Run 正在正常执行，更不能自动解决任务超时、租约过期和进程重启后的恢复问题。

同样，`SmartJobService` 和 `SmartJobExecutor` 是动态定时任务管理能力，也不是 Agent Run 状态机。

这些能力名称相似，但业务语义完全不同。后续 Runtime 仍然需要自己的持久化状态、执行心跳、租约和恢复机制。

### 5. 文件 Key 不等于文件访问权限

`FileService` 已经统一了文件元数据和存储操作，但部分 URL 获取和下载入口并没有统一接收当前用户身份。

因此，业务不能仅凭拿到一个 File Key，就推定当前用户有权访问对应文件。尤其是 Agent 工具处理用户上传内容时，还要校验文件归属和访问策略。

这些发现没有在本次盘点中直接修复。它们被记录为后续独立审查和优化事项，避免把“发现问题”和“获得修改授权”混为一谈。

## 四、怎样把盘点结果变成 AI 真正会遵守的规则

只写一份能力文档还不够。

如果它只是放在 `docs/` 里，开发 Agent 未必每次都会主动读取。更实际的做法，是让项目入口规则明确要求它在新增功能前先查这份清单。

因此，本次新增了：

`docs/architecture/reusable-capabilities.md`

这份文档不仅列出能力，还记录源码入口、复用方式、适用边界、当前状态和已经发现的风险。

同时更新了根目录的 `AGENTS.md`，增加“现有能力优先复用”约束：

1. 新增功能前先阅读能力资产清单。
2. 继续检索源码调用点、Bean 装配、配置、数据表和权限上下文。
3. 优先直接复用；不够时再考虑扩展。
4. 如果已有实现存在缺陷，先提交问题、影响和优化方案。
5. 未经明确确认，不得借新功能开发之名复制、替换、重写或顺手重构已有实现。
6. 新增或调整公共能力后，同步维护能力清单。

这套规则背后的判断顺序是：

~~~text
需求进入
   ↓
检索现有能力与调用链
   ↓
现有能力是否满足？
   ├── 是 → 直接复用
   └── 否
        ↓
是否能兼容扩展？
   ├── 是 → 提出扩展方案
   └── 否
        ↓
发现现有实现缺陷？
   ├── 是 → 记录问题，单独评审和授权
   └── 否 → 说明原因后新增能力
~~~

这里有一个我特别在意的点：**发现旧代码有问题，不代表可以在当前需求里顺手重构它。**

新功能的交付范围应该是可控的。否则一个看似简单的需求，很容易演变成对公共基础设施的大规模修改，风险和审查成本都会失控。

## 五、能力清单也需要有状态，不能只标记“已有”

我没有把所有能力统一标记成“可复用”，而是区分了几种状态：

| 状态 | 含义 |
|---|---|
| 可复用 | 已找到清晰入口和使用方式，接入时仍需验证当前环境 |
| 需验证 | 实现存在，但配置、运行条件或调用上下文尚未确认 |
| 建议优化 | 已发现明确的实现风险，需要单独评审 |
| 暂不复用 | POC、Mock、历史遗留或不属于当前产品范围 |

这能避免另一个常见问题：文档把一个类记录成“已有能力”，后续 AI 就把它理解为“可以直接投入生产”。

比如，POC 里已经有 Run 管理和 SSE 订阅相关代码，前端也已经有 Mock Run 状态。这些都能帮助理解方案、验证交互，但不能因此认定正式后端已经具备完整的 Session / Run 闭环。

同样，数据库脚本里有 44 张表，也不代表这些表都对应当前仍在使用的业务功能。历史 SQL 包含 DROP TABLE 和范围外数据，不能被当作生产增量迁移脚本直接执行。

能力状态应该由证据决定，而不是由类名、目录名或文档描述决定。

## 六、后续开发应该怎样使用这份清单

我希望这份文档不是一次性盘点报告，而是 AgentKit 后续开发的一份长期工程索引。

每次新增功能，至少完成以下检查：

- [ ] 先查能力清单，定位相关 Service、工具、组件和配置。
- [ ] 检索实际调用点，确认 Bean 是否注册、条件装配是否满足。
- [ ] 检查数据库表、Mapper XML、Redis Key 和序列化方式。
- [ ] 检查当前执行上下文：HTTP 还是后台线程，是否依赖 ThreadLocal。
- [ ] 检查身份、权限、数据归属和事务边界。
- [ ] 检查并发、幂等、超时、资源释放和故障处理。
- [ ] 区分正式代码、POC、Mock 和预留 API 契约。
- [ ] 在 PR 中说明选择复用、扩展、优化还是新增，以及原因。

如果新增了一个公共能力，就要补充它的入口、配置、使用方式和限制；如果一个能力从“需验证”变成“可复用”，也应该有构建、启动或业务场景的验证证据。

这样，能力清单才能随着代码一起演进，而不是很快变成另一份过期文档。

## 八、最后一点想法

过去做 AI Coding，很容易把注意力放在 Prompt 怎么写、模型怎么选、Agent 怎么分工，以及怎样让它一次性生成更多代码。

但随着项目变大，我越来越觉得，决定 AI Coding 质量的一个基础问题是：**AI 是否真正理解当前项目的工程事实。**

如果它不知道已有 Service，就会重新造一个；不知道身份来自哪里，就会绕过权限上下文；不知道 Mock 和正式接口的区别，就可能把页面演示当成业务交付；不知道现有代码的缺陷，就可能把不安全的实现复制到更多地方。

所以，我更愿意把能力资产清单看作项目的一部分工程记忆：

- 让 AI 知道已有能力在哪里。
- 让它知道哪些能力可以复用、哪些需要谨慎。
- 让它在发现问题时先报告，而不是擅自重构。
- 让后续开发持续更新这份事实索引。

**好的 AI Coding，不只是让 AI 更快地写出代码，而是让它在理解现有工程的基础上，做出更少重复、更少越界、更容易维护的改动。**

这也是我希望 AgentKit 后续开发逐步形成的工作方式。
