# AgentKit v0.1：从 ReAct POC 到 Java Agent Runtime

**一次围绕 Agent 执行生命周期、数据一致性与 SSE 恢复的工程实践**

- 项目：[neilyoli/agentkit](https://github.com/neilyoli/agentkit)
- 版本基线：`main@24d45f294bb9c19aad1d0c12aa37543ce8622817`（PR #32）
- Java 21 / Spring Boot 4.1.2
- AgentScope Java 2.0.5
- DeepSeek `deepseek-flash`
- MySQL 8 / Redis
- React 19 / TypeScript / Vite

---

## 一、为什么要做 AgentKit

AgentKit 是一个面向企业内部使用的通用 Agent 工作台。

项目开始时，我对建设顺序有一个比较明确的要求：先把 Agent 的执行底座搭建好，再考虑业务能力。未来无论是 Listing 生成、会议 Agent，还是其他业务 Agent，都应该能够运行在同一套执行环境中。

所以 v0.1 没有急着实现 Agent 管理、Skill 管理、MCP 管理和知识库，而是先解决一个基础问题：

**用户提交一个任务之后，后端能否可靠地执行它，并让执行过程可以查询、取消、在浏览器断线后恢复展示和管理？**

这件事情看起来只是一次模型调用，真正放进企业系统后，却会遇到不少工程问题：

- 用户提交任务后，HTTP 请求应该一直等模型完成，还是立即返回？
- 用户关闭浏览器，后台任务是否继续执行？
- 用户重复点击发送，如何避免同一个任务执行两次？
- 同一个会话同时提交两个任务，应该如何处理？
- 模型正在输出时用户点击取消，如何避免取消与完成竞争？
- SSE 断开或者浏览器刷新，如何恢复已经持久化的消息和后续事件？
- 服务重启时，如何处理未完成任务，避免新旧实例同时执行？
- 多个用户同时使用，如何限制模型调用和线程资源？

这些问题决定了 v0.1 真正要交付的东西：一条完整的执行链路。

`HTTP 提交 → Run 持久化 → 后台执行 → AgentScope → DeepSeek → 工具调用 → 事件持久化 → SSE 推送 → 结果归档`

## 二、v0.1 是怎样一步步建设起来的

整个过程不是从正式业务代码直接开始，而是先验证技术组合，再建立工程基线，最后实现运行时。

```text
M0 独立 POC
  ↓
M1-A 工程兼容性
  ↓
M1-B 数据、API、状态机和 SSE 契约冻结
  ↓
M1-C Session / Run / Message / Event 持久化
  ↓
M2 AgentScope Runtime 与平台工具
  ↓
M3 Run 托管、取消、SSE 与实例生命周期
  ↓
M4 工作台真实 API 联调
  ↓
M5 真实场景验收与运维交接
```

### 2.1 M0：先验证 AgentScope 是否真的能用

正式建设之前，我创建了独立的 `poc/` 工程。POC 与正式的 `agentkit-server/` 隔离，不把实验代码直接作为生产代码使用。

当时要验证的组合是 Java 21、Spring Boot 4.1.2、AgentScope Java 2.0.5、ReActAgent、DeepSeek，以及 Spring MVC + SSE。

验证重点不是依赖能不能下载，而是实际执行：

1. 使用 DeepSeek 的 OpenAI 兼容接口，通过 `OpenAIChatModel` 和 `DeepSeekFormatter` 完成真实问答。
2. 让模型根据用户问题自行选择 `get_current_time` 工具，将工具结果重新交给模型，验证完整 ReAct 循环。
3. 验证模型文本增量、工具调用开始和结束、模型调用结果等事件。
4. 通过 AgentScope 的 `AgentRun` 句柄取消执行，观察底层管线真实退出。
5. 模拟浏览器断开，验证后台任务是否继续，以及重新连接后能否按事件序号恢复。
6. 验证操作系统文件锁、第二实例拒绝启动、进程异常退出后锁释放等行为。

POC 阶段还发现了几个直接影响正式架构的问题：

- `ExecutionConfig.timeout` 实际是相邻流式信号之间的超时，不是 Run 总执行时间限制。
- AgentScope 存在 SDK 内部会话执行闸门，被取消的任务可能继续占用内部会话资源。
- 取消操作不能保证立即终止不可中断的外部 I/O。
- SDK 异常可能经过重试包装，需要区分模型真实错误与 SDK 外层错误。

例如，正式 Runtime 没有继续使用相同的 SDK Session ID，而是将平台 Session ID 与 Run ID 组合，避免已取消任务影响同一会话的新任务。

POC 最终保留为独立验证工程，正式实现按照平台契约重新组织。

### 2.2 M1-A：先解决现有工程兼容性

AgentKit 后端并不是从零开始。通过 PR #15，我们将 SmartAdmin v3.0.0 后端迁入 `agentkit-server/`，保留原有企业管理和基础设施代码。

迁移包括 Sa-Token 登录认证、员工、部门、岗位、角色、菜单、MyBatis-Plus、Redis、Druid、文件服务、缓存和其他平台支撑能力。

随后通过 PR #17 建立 AgentScope 兼容性探针，在原有 Java 工程依赖图中验证 SDK 初始化；PR #18 再将正式工程升级至 Java 21 和 Spring Boot 4.1.2。

这里有一个容易忽略的问题：Spring Boot 4 的 JSON 依赖体系发生变化，而现有项目的 Redis 会话序列化仍然依赖 Jackson 2。因此升级时没有直接重写所有序列化逻辑，而是使用 Jackson 2 兼容模块，保留原有 Sa-Token Redis 数据格式。

PR #28 最终完成本地隔离环境验收：MySQL 8.4.13、Redis 7.4、Admin 完整上下文启动、Sa-Token 登录态读写、Jackson HTTP JSON 行为，以及 AgentScope 2.0.5 最小装配探针。

当时 GitHub Actions 没有成功分配 Runner，因此本地验收结果不能写成 CI 通过。

### 2.3 M1-B：先把业务契约确定下来

这一步是整个项目中非常重要的设计工作。在正式开发 Agent Runtime 之前，先确定：

- Session、Run、Message、Event 四类数据的关系；
- Run 状态机；
- Idempotency-Key 行为；
- HTTP API；
- SSE 事件协议；
- 用户身份与资源归属；
- 数据库事务边界；
- 服务重启和取消行为。

这些内容会同时影响后端、前端、Runtime 和数据库。如果后端按一种状态机实现，前端按另一种状态机编写，最后再靠联调修正，成本会很高。

所以 M1-B 先形成统一契约，后续实现都以它为依据。

### 2.4 M1-C：先让数据和查询能力独立运行

M1-C 没有急着接入 AgentScope，而是先实现 Session、Run、Message、Event 数据结构，以及 Session、消息历史和快照查询 API。

同时完成 Flyway 迁移、Owner 归属校验、Agent 专属错误响应、现有 Sa-Token Bearer 认证复用和 Springdoc `agent-runtime` API 分组。

这为后续 Runtime 提供了稳定的数据基础。

### 2.5 M2-M5：统一完成端到端实现

M2、M3、M4、M5 最终合并成一份完整实施计划。PR #31 统一实施范围，使用一条分支、一个 Worktree 和一个连续实施过程，最后由 PR #32 统一交付。

这样做主要是为了避免阶段计划分散、同一份架构定义被多处修改、AI 编码过程丢失已经确认的要求，以及前后端对同一个接口产生不同理解。

PR #32 最终完成正式 Runtime、Run 后台托管、SSE、工作台联调和完整验收。

## 三、后端工程结构：为什么保留两个 Maven 模块

v0.1 最终采用两个 Maven 模块：

- `agentkit-base`
- `agentkit-admin`

没有为了 Agent 功能再拆出独立 Maven Runtime 模块。

当前父工程坐标：

```xml
<groupId>cn.tomeet</groupId>
<artifactId>agentkit-parent</artifactId>
<version>3.0.0</version>
<packaging>pom</packaging>
```

这里的 `3.0.0` 是 Maven 构件版本，不代表 AgentKit 产品版本。

![AgentKit Maven 模块与代码边界](/images/posts/agentkit-v0.1/01-modules.svg)

### 3.1 两个模块分别负责什么

| 模块 | 职责 |
|---|---|
| `agentkit-base` | 公共类型、基础设施配置和平台支撑能力 |
| `agentkit-admin` | AdminApplication、HTTP 入口、企业管理业务和 Agent 业务 |

依赖方向是 `agentkit-admin → agentkit-base`。

base 不是一个纯工具包：它已经包含 MVC、Redis、MyBatis、文件存储和支撑业务。当前不恢复四模块或八模块设计。

### 3.2 Agent 代码按职责分包

正式 Agent 业务位于：

```text
cn.tomeet.agentkit.admin.module.agent
├── api/             身份解析、错误处理
├── session/         会话管理
├── run/             Run 受理、状态和执行存储
├── message/         公开消息
├── event/           事件持久化与 SSE
├── runtime/
│   ├── executor/    后台执行协调
│   ├── instance/    实例生命周期与独占锁
│   └── agentscope/  AgentScope SDK 适配
└── tool/            平台工具契约与实现
```

这些目录是职责边界，不是为了分层而分层。各功能按需要建立 Controller、Service、DAO 和 domain；Manager 只用于确实需要协调多表原子操作的地方。

### 3.3 为什么不再拆 Maven 模块

AgentScope 是 Agent 领域的技术依赖，但 Agent 业务目前仍属于企业管理应用的一部分。

如果为了追求模块数量，将它提前拆成 core、runtime、infra、app，就要额外处理模块依赖、Spring Bean 装配、配置管理和事务边界。目前没有证据证明这些边界需要独立发布或者独立部署。

因此 v0.1 保留两个 Maven 模块，在 `module.agent` 内建立清晰的职责边界。真正需要独立部署 Runtime，或者多个应用共享同一套 Agent 执行能力时，再考虑拆分。

### 3.4 技术基线

| 技术 | 版本 / 用途 |
|---|---|
| Java | 21 |
| Spring Boot | 4.1.2 |
| Spring MVC | HTTP 接口与 SSE |
| AgentScope Java | 2.0.5 |
| MyBatis-Plus | 3.5.18.1 |
| Sa-Token | 1.46.0 |
| Redis | 登录态、缓存 |
| MySQL | Agent 运行事实 |

## 四、后端整体架构：平台负责执行生命周期，SDK 负责 Agent 执行

v0.1 的后端主要分为四个部分：HTTP 与业务入口、Run 生命周期管理、Agent Runtime 适配、数据持久化和事件输出。

![AgentKit v0.1 后端组件架构](/images/posts/agentkit-v0.1/02-backend-architecture.svg)

这张图展示的是后端组件之间的调用关系，不等同于完整的系统部署视图。完整系统图、Maven 边界、UML 时序图和状态图均保留为可编辑 Mermaid 源码，见[架构图与时序图源文件](https://github.com/neilyoli/blog/blob/docs/agentkit-v0.1-runtime-article-20261124/docs/diagrams/agentkit-v0.1.md)。

这张图有一个关键点：

**AgentScope 负责执行 Agent，平台负责管理 Run。**

Session、Run、Message、Event 的业务事实由 AgentKit 管理。AgentScope 提供模型调用、ReAct 执行和工具调度能力。平台不把 SDK 内部对象直接暴露给 Controller、Service 或数据库模型。

### 4.1 HTTP 层只负责接入

主要入口：

- `AgentSessionController`：会话查询、创建和快照；
- `AgentRunController`：Run 提交、查询和取消；
- `AgentEventStreamController`：SSE 事件订阅。

认证沿用现有 Sa-Token Bearer Header。Agent API 的错误响应独立处理，不改造历史 Admin 接口的响应协议。

### 4.2 应用层管理 Run

`AgentRunService` 负责业务编排，`AgentRunAdmissionTransaction` 负责受理事务，`AgentRunExecutor` 负责后台执行调度。

执行期间，`AgentRunExecutionListener` 接收 Runtime 事件，将公开事件、文本快照和最终结果写入数据库。

SSE 服务只读取已经提交的事件，不参与模型执行。

### 4.3 数据层的职责

MySQL 保存 Session、Run、Message、Event，是运行事实来源。

Redis 继续承担 Sa-Token 登录态和现有缓存职责，不作为 Run 状态、幂等记录或事件序号的唯一来源。

## 五、四张核心表：把 Agent 运行事实持久化

我们没有将一次对话简单保存为一个 JSON 字段，而是将会话、执行、消息和事件分别建模。

![Session、Run、Message、Event 数据关系](/images/posts/agentkit-v0.1/03-data-model.svg)

| 表 | 职责 | 核心字段 |
|---|---|---|
| `agent_session` | 一段持续对话 | owner、title、active_run_id、message_sequence |
| `agent_run` | 一次任务执行 | request_key、input_digest、status、finish_reason、usage |
| `agent_message` | 用户输入和公开回答 | session_id、run_id、sequence、role、content、complete |
| `agent_event` | 执行过程中的公开事件 | run_id、sequence、event_type、payload |

### 5.1 为什么要区分 Message 和 Event

Message 保存对话内容。例如用户输入和 AI 最终回答。

Event 保存执行过程。例如：

```text
run.accepted
run.started
message.started
tool.started
tool.completed
message.delta
message.completed
run.completed
```

Message 用于恢复对话历史，Event 用于恢复执行进度。两者职责不同，不能用一张表代替。

### 5.2 为什么 Run 不保存 input_text 和 output_text

v0.1 的设计中，Message 是公开文本的唯一事实来源：

- 用户输入保存在 USER Message；
- AI 回答保存在 ASSISTANT Message；
- Run 负责记录状态、终止原因、用量和执行元数据；
- Event 负责记录公开执行事件。

这样可以避免同一份对话内容在多个地方重复维护。

### 5.3 关键数据库约束

幂等约束：

```sql
UNIQUE (owner_type, owner_id, session_id, request_key)
```

消息序号约束：

```sql
UNIQUE (session_id, sequence)
```

同一个 Run 的消息约束：

```sql
UNIQUE (run_id, role)
```

事件序号约束：

```sql
UNIQUE (run_id, sequence)
```

这些约束让数据库成为关键写入路径的一致性裁决者。幂等键和消息、事件序号由唯一约束兜底；Session 占用通过条件 UPDATE 保证同一 Session 只有一个 Run 能成功占用。

### 5.4 数据库迁移和时间约定

Agent 表采用 Flyway。存量数据库通过 `baseline-on-migrate=true`、`baseline-version=1` 管理，Agent 表从 `V2__create_agent_tables.sql` 开始迁移。

应用侧显式写入 UTC 时间，再将时间以 ISO-8601 格式返回前端，避免数据库会话时区与应用时区混乱。

v0.1 不提供 Session 删除、归档和自动清理功能，也不自动清理历史 Event。

## 六、Run：整个执行系统的核心

理解 AgentKit 的关键，是理解 Run。

Session 表示持续对话；Run 表示用户在这个对话中提交的一次执行。一次用户发送消息，对应一个 Run。一个 Session 可以有多个 Run，但同一时间只允许一个活动 Run。

### 6.1 Run API

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/agent/sessions/{sessionId}/runs` | 提交任务 |
| GET | `/agent/runs/{runId}` | 查询执行状态 |
| POST | `/agent/runs/{runId}/cancel` | 取消任务 |
| GET | `/agent/runs/{runId}/events` | 订阅执行事件 |

提交接口使用 `Idempotency-Key` Header：

```http
POST /agent/sessions/{sessionId}/runs
Authorization: Bearer <token>
Idempotency-Key: <UUID>
Content-Type: application/json
```

请求：

```json
{
  "input": "帮我查询上海当前时间"
}
```

成功返回 HTTP `202 Accepted`。它只表示任务已经成功受理，不表示模型已经执行完成。

### 6.2 幂等机制

前端每次主动发送消息，生成一个 UUID 作为 `Idempotency-Key`。

- 网络重试：复用原来的 Key。
- 用户主动重新发送：生成新的 Key。

后端还会对原始输入的 UTF-8 字节计算 SHA-256 摘要，不进行 trim、换行替换或 Unicode 规范化。

| 请求 | 结果 |
|---|---|
| 同 Key、同输入 | 返回原 Run |
| 同 Key、不同输入 | 409 INPUT_CONFLICT |
| 不同 Key、同 Session 且已有活动 Run | 409 SESSION_BUSY |
| 不同 Key、不同 Session | 在资源允许时并行 |

这样既能避免网络重试重复执行，也不会错误地将用户主动发送的相同文本识别为重复任务。需要注意，幂等唯一约束只约束同一 Owner、Session 和 Key；它不替代 Session 占用条件更新。

### 6.3 Session 原子占用

这里使用数据库条件更新：

```sql
UPDATE agent_session
SET active_run_id = :runId
WHERE id = :sessionId
  AND owner_type = :ownerType
  AND owner_id = :ownerId
  AND active_run_id IS NULL;
```

只有影响一行，才代表当前 Run 成功占用了 Session。

如果只在 Java 中先查再写，两个请求可能同时读取到 `active_run_id = NULL`，然后都认为自己能够执行。数据库条件更新可以保证只有一个请求成功占用。

这里没有引入 Redis 锁，也没有使用 `SELECT FOR UPDATE`。

### 6.4 受理事务

![Run 受理事务流程](/images/posts/agentkit-v0.1/04-admission-transaction.svg)

一次 Run 受理过程可以概括为：

1. 获取当前登录员工身份，检查员工是否有效。
2. 校验 Session 所有权。
3. 检查 Idempotency-Key 和输入摘要。
4. 检查全局及用户级执行容量。
5. 创建 ACCEPTED Run。
6. 条件更新 Session.active_run_id。
7. 分配消息序号，创建 USER Message。
8. 分配事件序号，创建 run.accepted Event。
9. 提交数据库事务。
10. 事务提交成功后，派发后台任务。

唯一键冲突需要先回滚当前事务，再重新查询原 Run，不能在已经标记 rollback-only 的事务中继续查询。

整个受理事务保证：**Run、Session 占用、用户消息和受理事件要么一起提交，要么一起回滚。** 但后台派发发生在事务提交之后，两者不是一个原子事务。如果进程恰好在提交后、派发前退出，Run 会在下一次启动时被识别为遗留非终态并收敛为 INTERRUPTED，不会自动重放。

模型调用不在这个事务里面。

### 6.5 Run 执行时序

```text
用户
  │ POST /runs + Idempotency-Key
  ▼
AgentRunController
  │
  ▼
AgentRunService
  │
  ▼
AgentRunAdmissionTransaction
  ├── 幂等预查
  ├── 容量检查
  ├── 插入 ACCEPTED Run
  ├── 条件占用 Session
  ├── 写 USER Message
  └── 写 run.accepted Event
        │ COMMIT
        ▼
   AgentRunExecutor
        │ 条件领取 ACCEPTED → RUNNING
        ▼
    AgentRuntime
        │
        ▼
 AgentScopeRuntimeService
        │
        ▼
 DeepSeek / Toolkit
        │
        ▼
 AgentRunExecutionListener
        ├── 公开事件
        ├── Assistant 文本快照
        └── 终态事务
```

HTTP 受理后返回 Run ID 和当前状态（正常受理为 202）。后台执行器独立运行，不占用原始 HTTP 请求等待模型。派发与 HTTP 响应存在并发关系：后台线程可能在 202 返回前已经开始执行。

### 6.6 有界执行资源

v0.1 对执行资源进行了限制：

| 配置 | 默认值 |
|---|---:|
| 全局活动 Run | 4 |
| 单用户活动 Run | 2 |
| 后台执行线程 | 固定 4 |
| 单 Run 事件上限 | 5000 |
| 单次输入长度 | 32000 字符 |

后台执行器采用固定大小线程池和 `SynchronousQueue`，不允许通过无限制排队掩盖容量不足。需要区分两种限制：数据库中的全局 / 用户活动 Run 数是受理阶段的预检查，并发请求可能同时通过；固定线程池才是实际执行并发的硬上限。线程池满或关闭中导致派发失败时，Run 会收敛为可查询的启动拒绝。

派发失败时，Run 会收敛为 `FAILED / START_REJECTED`。用户能够通过 Run 查询接口知道任务失败，而不会看到一个永远停留在 ACCEPTED 的任务。

## 七、AgentScope Runtime：将 SDK 隔离在适配层

这是后端最重要的技术边界之一。

项目没有让 `AgentRunService` 直接创建 `ReActAgent`，而是先定义平台自己的 Runtime 接口。

```text
module.agent.runtime
  AgentRuntime
  AgentExecutionRequest
  AgentExecutionHandle
  AgentExecutionResult
  AgentRuntimeEvent
  AgentRuntimeListener
  AgentRuntimeProperties
```

其中：

- `AgentRuntime`：执行入口；
- `AgentExecutionRequest`：一次执行所需的输入、身份和上下文；
- `AgentExecutionHandle`：控制单次执行，包含取消能力和退出确认；
- `AgentExecutionResult`：执行最终结果；
- `AgentRuntimeEvent`：SDK 无关的内部事件；
- `AgentRuntimeListener`：接收执行事件与完成结果。

真正的 AgentScope 适配边界位于：

```text
module.agent.runtime.agentscope
```

`AgentScopeRuntimeService` 是正式生产代码中唯一直接引用 `io.agentscope.*` 的位置。

这样做有两个直接好处：Run 执行器不需要理解 AgentScope 的内部事件类型；后续增加其他 Runtime 实现时，可以继续使用相同的平台执行接口。

### 7.1 每次 Run 创建一次性 ReActAgent

正式实现中，每次提交 Run 都会组装一次执行实例：

```java
ReActAgent agent = buildAgent(apiKey, request.priorTerminationNote());

RuntimeContext context = RuntimeContext.builder()
        .userId(request.owner().ownerType() + ":" + request.owner().ownerId())
        .sessionId(request.sessionId() + "-" + request.runId())
        .build();

return agent.prepareRun(buildMessages(request), context);
```

这里有一个细节：SDK 内部的 Session ID 使用 `sessionId + "-" + runId`，而不是直接使用平台 Session ID。

原因是平台已经通过数据库保证同一个 Session 同时只有一个活动 Run。如果 SDK 再使用相同 Session ID 管理执行，之前已取消但尚未释放内部执行资源的任务，可能影响同一 Session 的新任务。

因此，平台 Session 负责业务串行，SDK Session 按 Run 隔离。

### 7.2 模型配置

| 配置 | 值 |
|---|---|
| Provider | DeepSeek |
| API 协议 | OpenAI Compatible |
| Base URL | `https://api.deepseek.com` |
| Model | `deepseek-flash` |
| Formatter | `DeepSeekFormatter` |
| Stream | true |
| Max Iterations | 8 |
| Context Window Size | 1048576 |
| Model Signal Timeout | 120 秒 |
| Model Max Attempts | 1 |

API Key 从 `DEEPSEEK_API_KEY` 环境变量读取。配置文件只保存环境变量名称，不保存真实模型密钥。

需要特别说明：120 秒是模型流式信号间隔超时，不是 Run 总执行时间上限。这是 M0 POC 阶段发现、正式实现中保留的边界。

### 7.3 多轮上下文如何构建

平台不会将 AgentScope 内部 Session 当作对话事实来源。每次创建 Run 时，都会从数据库加载历史消息，再组装成模型输入。

上下文只使用已完成的 USER 和 ASSISTANT Message。默认保留最近 200 条消息，最大字符预算为 200000。

如果上一轮执行失败、取消或者中断，用户输入仍然保留，但未完成的 ASSISTANT 回答不作为完整历史消息注入下一轮。

Runtime 会在内部系统提示中补充上一轮的终止说明。这段说明不写入公开 Message，也不会暴露给前端。

### 7.4 工具注册体系

工具单独建立平台契约：

```text
module.agent.tool
  AgentTool
  AgentToolDescriptor
  AgentToolRegistry
  AgentToolConfig
  GetCurrentTimeTool
```

工具由平台管理，AgentScope 只负责调用。

核心设计是显式注册：只有 `AgentToolConfig.agentPlatformTools` 清单 Bean 中声明的工具，才会暴露给模型。即使某个工具类已经被 Spring 注册成 Bean，也不会自动成为模型可调用的工具。

![AgentScope Runtime 与平台工具桥接](/images/posts/agentkit-v0.1/05-runtime-tool-bridge.svg)

`AgentScopeToolBridge` 负责将平台工具转换成 AgentScope 工具接口。工具执行统一经 `AgentToolRegistry` 路由，复用未注册拦截和异常脱敏。

### 7.5 首个平台工具：get_current_time

v0.1 没有一开始就开放大量高权限工具。首个工具是 `get_current_time`。

输入：

```json
{
  "timezone": "Asia/Shanghai"
}
```

工具执行顺序：

1. 检查参数是否存在。
2. 检查时区字符串长度。
3. 验证 IANA Zone ID。
4. 检查企业时区白名单。
5. 使用注入的 Clock 获取当前时间。
6. 返回结构化时间信息。

返回结果包含 UTC 时间、目标时区本地时间、UTC 偏移和时区 ID。

如果白名单为空，拒绝全部查询；如果时区不合法或者不在白名单中，也不会退回服务器默认时区。

这个工具不访问数据库、Redis 或网络，没有外部副作用。工具超时统一由 SDK 执行边界控制，默认 2000ms，而不是让每个工具自行实现一套超时机制。

## 八、执行结果如何持久化：Message Snapshot 与 Event

模型是流式输出的。如果每收到一个 Token 就写一次数据库，数据库写入次数会非常多。

v0.1 采用内存累计、低频快照的方案。

### 8.1 AgentRunExecutionListener

Runtime 产生的事件交给 `AgentRunExecutionListener`，它负责：

- 累计文本增量；
- 记录工具开始和结束事件；
- 累计 Token Usage；
- 生成 Assistant Message；
- 定期保存回答快照；
- 提交最终结果；
- 处理取消与完成竞争。

### 8.2 快照策略

默认规则：

```text
每 1000ms
或者
累计新增 256 个 Unicode 码点
满足任意一个条件，就保存一次完整文本快照。
```

例如模型正在输出：

```text
你好，我可以帮你查询当前时间。
```

第一次写入：

```text
content = "你好，我可以"
complete = false
```

下一次快照：

```text
content = "你好，我可以帮你查询当前时间。"
complete = false
```

同时产生一条 `message.delta`。Event 中的 delta 只表示本次新增文本；Message 保存的是完整快照。两者在同一个数据库事务中提交。

这样既减少频繁数据库写入，也让浏览器刷新后能够恢复已经保存的回答。注意：尚未达到快照阈值的内存增量，在进程崩溃前并未持久化，不能保证恢复。

### 8.3 执行结束

成功时，一个终态事务完成：

1. 强制保存最后一批文本；
2. 将 Assistant Message 标记为 complete=true；
3. 写入 message.completed；
4. 更新 Run 终态；
5. 写入 run.completed；
6. 按当前 Run ID 释放 Session.active_run_id。

失败、取消和中断时，保留最近一次回答快照，但 complete=false。用户仍然能够看到任务已经生成的部分内容。

### 8.4 Token Usage

模型调用结束后，从 AgentScope 的 `ModelCallEndEvent` 获取 Token Usage。

如果供应商提供真实 Usage，就标记 `provider-reported`；如果没有可靠数据，则标记 `unknown`。未知用量不直接记成 0。

这是后续统一模型网关和 Token 计费治理需要的基础。

## 九、SSE：浏览器断开，Run 仍然继续执行

SSE 的实现也是 v0.1 的重点。

**SSE 连接只负责展示执行进度，不负责驱动 Agent 执行。**

### 9.1 为什么不能让 SSE 控制 Run

假设用户提交任务后，后端开始调用 DeepSeek，用户关闭浏览器，SSE 连接断开。此时 Run 应该继续执行。

因此，Run 的生命周期属于后台执行器，而 SSE 只是一个订阅者。没有订阅者，任务也必须继续执行，并将结果保存到数据库。

### 9.2 为什么使用 fetch + ReadableStream

浏览器原生 EventSource 不支持自定义 Authorization Header，而 AgentKit 使用现有 Sa-Token Bearer 认证。

因此前端采用 `fetch + ReadableStream`，请求时同时携带：

```http
Authorization: Bearer <token>
Last-Event-ID: 12
```

Token 不放在 URL 或 Query 参数中。

### 9.3 数据库轮询

正式实现没有引入 Redis Pub/Sub、消息队列或进程内事件通知队列。SSE 服务直接轮询 MySQL：

| 参数 | 默认值 |
|---|---:|
| 轮询间隔 | 500ms |
| 单批事件数 | 100 |
| 心跳 | 15 秒 |
| 单 Run 最大订阅 | 8 |
| 全局最大订阅 | 32 |

查询条件：

```sql
SELECT *
FROM agent_event
WHERE run_id = :runId
  AND sequence > :lastSequence
ORDER BY sequence ASC
LIMIT 100;
```

数据库是事件事实来源。事件写入和序号递增在同一个事务内，SSE 只读取已经提交的事件。重连过程不依赖服务器内存中是否还保存着之前的事件。

### 9.4 Snapshot 与断线恢复

页面刷新时，前端首先调用：

```http
GET /agent/sessions/{sessionId}/snapshot
```

后端在一个 `REPEATABLE READ` 只读事务中返回 Session 信息、最新一页（最多 50 条）Message、是否还有更早历史、当前活动 Run 和 `resumeEventSequence`。

其中：

```text
resumeEventSequence = activeRun.eventCount
```

消息快照和事件游标来自同一个数据库一致性视图。

前端恢复历史消息后，再建立 SSE 连接：

```http
GET /agent/runs/{runId}/events
Last-Event-ID: <resumeEventSequence>
```

服务端只返回 `sequence > Last-Event-ID` 的事件，不会重复追加已经包含在 Message Snapshot 中的文本。整页刷新使用 Snapshot 的 `eventCount` 作为新游标；仅网络断开重连时，前端使用最后一条已成功应用的事件序号。

![Snapshot 与 SSE 断线恢复流程](/images/posts/agentkit-v0.1/06-sse-resume.svg)

完整 UML 时序图（包含刷新与网络断开两种分支）见[可编辑 Mermaid 源文件](https://github.com/neilyoli/blog/blob/docs/agentkit-v0.1-runtime-article-20261124/docs/diagrams/agentkit-v0.1.md#9-核心业务时序图页面刷新与-sse-恢复)。

### 9.5 重连策略

前端采用简单退避：1s → 2s → 4s → 8s，之后最多 10s。

遇到 HTTP 401，停止重连，走现有登录失效流程。Run 已经终态时，重新查询 Run 和 Message，确保最终展示与数据库一致。

SSE 断开不会取消 Run、释放 Session、重新调用模型或重复执行工具。Snapshot 也不是完整 Event 回放：游标之前的工具进度事件不会重新播放，恢复的是消息、Run 状态以及游标之后的新事件。数据库读取失败时关闭连接，让前端重新读取 Snapshot 和 Run 状态。

## 十、Run 状态机与取消竞争

Run 的状态定义如下：

| 状态 | 含义 |
|---|---|
| ACCEPTED | 已受理，等待执行器领取 |
| RUNNING | 正在执行 |
| CANCELING | 已接受取消请求，等待执行退出 |
| SUCCEEDED | 成功 |
| FAILED | 失败 |
| CANCELLED | 已取消 |
| INTERRUPTED | 服务退出或进程中断 |

![Run 状态机](/images/posts/agentkit-v0.1/07-run-state.svg)

### 10.1 取消请求不代表执行已经停止

用户调用：

```http
POST /agent/runs/{runId}/cancel
```

如果 Run 处于 ACCEPTED，可以直接收敛为 CANCELLED。

如果处于 RUNNING，则先更新为 CANCELING，再通知底层执行句柄取消。这里不能提前释放 Session，因为底层模型调用或者工具执行可能仍然没有退出。

只有最终终态事务成功提交后，才允许释放 Session 占用。

### 10.2 取消与完成竞争

例如线程 A 中模型执行完成，线程 B 中用户点击取消。两边可能同时尝试更新 Run。只有数据库条件状态更新成功的一方能够提交对应终态；若取消先将 RUNNING 推进为 CANCELING，模型随后返回成功也不能覆盖取消结果。

因此状态转换使用数据库条件更新。谁先成功提交，谁决定最终结果。后到的请求读取当前状态，不得重复写入终态事件，也不能覆盖已经提交的终态。

`AgentRunExecutionListener` 还使用完成回调防重机制，避免 SDK 迟到的回调造成重复收敛。

这部分代码主要分布在：

- `AgentRunService`
- `AgentRunExecutionListener`
- `AgentRunExecutionStore`

## 十一、服务启动和关闭：单实例运行保护

v0.1 的部署目标是单企业、单实例，没有实现多节点调度或自动故障切换。

但即使是单实例，也需要处理服务重启时正在执行的 Run。

### 11.1 操作系统文件锁

通过 `FileChannel.tryLock()` 实现单实例独占。

锁文件只记录 PID 供人工排查，真正的独占判据是操作系统文件锁。第二个实例启动时，如果无法获得锁，就拒绝启动。

### 11.2 启动过程

```text
应用启动
  ↓
获取操作系统独占锁
  ↓
检查是否有遗留非终态 Run
  ↓
将遗留 Run 标记为 INTERRUPTED
  ↓
释放对应 Session 占用
  ↓
完成启动收敛
  ↓
开放服务
```

只有取得独占资格并完成遗留任务收敛后，实例才可以受理新任务。

### 11.3 关闭过程

![单实例启动与关闭生命周期](/images/posts/agentkit-v0.1/08-instance-lifecycle.svg)

这里有两个不同的等待目标：

- 等待 Run 状态收敛；
- 等待底层 Agent 执行管线真正退出。

二者不能混为一谈。如果执行还没有确认退出，系统就会扣留独占锁，不允许新实例提前接管。进程真正退出后，操作系统负责释放文件锁。

### 11.4 重启后的行为

如果发生 SIGKILL：

1. 操作系统释放文件锁；
2. 新实例获得独占资格；
3. 扫描遗留非终态 Run；
4. 将其标记为 `INTERRUPTED / APP_RESTARTED`；
5. 释放对应 Session 占用；
6. 允许用户重新提交任务。

v0.1 不会自动重放之前的模型调用或工具操作。已经保存的历史和会话展示状态可以恢复，正在执行的 Agent 不具备跨进程 Checkpoint 恢复能力。

## 十二、认证、权限与错误处理

AgentKit 沿用了现有 Sa-Token Bearer 认证体系，没有为了 Agent 工作台另外创建一套登录服务。

`AgentOwnerResolver` 负责解析当前登录员工身份。首期所有者类型固定为 `ADMIN_EMPLOYEE`。

写操作需要直接查询员工记录，确认员工存在、未删除、未禁用。Run 创建时保存 Owner 快照。后台执行不依赖 HTTP 请求中的 ThreadLocal，也不会将浏览器连接作为身份来源。

### 12.1 资源归属

Session、Run、Message 和 Event 查询都需要检查 Owner。如果资源不存在，或者资源属于其他用户，对外统一返回 404，避免通过资源 ID 枚举其他用户的数据。

### 12.2 Agent 专属错误信封

现有 Admin 接口保留原有 `ResponseDTO` 协议。Agent API 使用独立错误结构：

```json
{
  "error": "SESSION_BUSY",
  "message": "当前会话正在执行任务",
  "requestId": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
}
```

主要 HTTP 状态码：

| HTTP | 错误 |
|---|---|
| 400 | BAD_REQUEST |
| 401 | UNAUTHENTICATED |
| 403 | ACCESS_DENIED |
| 404 | SESSION_NOT_FOUND / RUN_NOT_FOUND |
| 409 | SESSION_BUSY / INPUT_CONFLICT |
| 422 | VALIDATION_FAILED |
| 429 | CAPACITY_EXCEEDED / TOO_MANY_SUBSCRIBERS |
| 503 | STORAGE_UNAVAILABLE / RUNTIME_UNAVAILABLE |
| 500 | INTERNAL_ERROR |

API 文档使用 Springdoc Code First，从 Controller、DTO 和校验注解生成。Agent 专属分组为 `/v3/api-docs/agent-runtime`。前端可以从运行中的后端生成类型，不需要长期维护另一份手写 OpenAPI 文件。

| 工程交付 | 架构文档、运行契约、运维手册和验收记录 |

有几个设计决定，我认为值得在后续版本中继续保持：

**1. 数据库负责运行事实。** Run 状态、幂等、消息序号和事件序号都由数据库保证。Redis 继续负责登录态和缓存，不承担另一套运行状态管理。

**2. Agent SDK 不能侵入业务层。** Runtime 接口与 SDK 适配层分离，AgentScope 类型不向其他业务包泄漏。

**3. 执行和展示分离。** 后台 Run 不依赖浏览器连接。SSE 只是事件订阅，浏览器刷新和断线都不会影响执行。

**4. 每个资源都应该有明确限制。** 模型调用、工具执行、后台线程、Run 并发、事件数量、SSE 连接和上下文长度，都需要有明确边界。

**5. 单实例能力要有明确的退出语义。** 标记任务中断不等于底层执行已经退出。只有确认执行退出，才能安全释放独占资格。

**6. 工程计划和代码必须能够互相验证。** 架构文档描述设计，代码体现实现，验收记录证明实际执行结果。三者不能相互替代。

## 结语

AgentKit v0.1 的工作主要集中在 Java 后端。

从最初的 AgentScope POC，到正式工程迁移，再到 Session、Run、Message、Event 的数据建模，最后完成 Agent Runtime、后台执行器、SSE 和单实例生命周期管理，整个过程逐渐明确了平台应该承担哪些职责。

目前的 v0.1 已经可以在单实例环境中完成真实模型调用、工具执行、后台任务管理、断线恢复和重启中断处理。

当然，它还没有解决多实例调度、Checkpoint 恢复、MCP、高权限工具、Skill 管理和知识库等问题。这些能力需要在后续版本中根据实际需求逐步建设。

对我来说，这个版本最重要的成果，是建立了一套可以继续扩展的 Agent 执行模型。后续无论增加什么业务能力，都可以沿着 Session、Run、Runtime、Tool 和 Event 这些已经明确的边界进行设计。

**代码负责执行，数据库负责记录事实，Runtime 负责连接模型与工具，平台负责管理整个任务的生命周期。**

这就是 AgentKit v0.1 的整体设计思路。
